Where "Suggested" comes from

At every pause, the analysis reviews this run's actual state — the question, the plan, what each step produced, earlier steering decisions — and may author extra suggestions, each with a concrete reason. The idea is sound; two things aren't. Copy: the authoring prompt is the orchestrator's internal decision prompt reused verbatim, so suggestions arrive in machinery language ("no triggers fired"). Validity: a live authored option was found carrying an invented action (`recover_full_text` — not a real capability; full text is already fetched through every known alternate location on the first pass, and paywall/dead-link failures don't improve on retry). The fix is backend-first (owner ruling): today free text is validated by the steering grammar with honest refusals, but authored options are only parse-checked and their stored deltas apply verbatim — an invented action becomes a silent no-op when picked. This slice closes that asymmetry in the substrate: one grammar, one validator, for all three option producers — authored options compile through the same grammar as free text at authoring time (non-compiling → dropped, logged, evented), the answer route revalidates on apply, and a delta the grammar can't compile is always a refusal with a reason, never a silent no-op. Plus the prompt rev: plain-language labels · reasons citing visible facts · machinery vocabulary banned · endorsements render as the reason under the blue primary · the block titled "Suggested from this run's results".

What "fired" means

always = every run stops at this point. fired = the run stops only when one of the point's pre-declared warning signals went off — deterministic checks over persisted records, with fixed thresholds — or when the orchestrator's boundary review promotes the stop. off = never stops (unattended). The signal sets per point: P1 — the search itself failed (database errors / zero usable documents). P2 — too few relevant documents survived screening · ≥70% of appraised documents scored weak · screening quality collapsed (≥20% failed or ≥50% demoted). P3 — a large theme was excluded from the reading list · something you nominated didn't make it · the pool was thin. Groups — the grouping run raised flags. Every boundary also checks the universal signal: an upstream step failed or was skipped. A "fired" cell therefore means: healthy runs flow through silently; a run with something off stops and shows you why.

The open question: how many stops in the default mode?

With P1 upgraded to a standing search review, a moderate-mode run would stop at P1 · P2 · P3 · (Groups+P4) — four interruptions on a standard run, five questions on a deep one. Each is now small and single-subject, so this may be right ("more, smaller, clearer decisions"). The alternative trims P2 to fired-only in moderate: it pauses only when its triggers fire (too few relevant · quality collapse), since P1 now covers "search more" early and P3 carries an escape hatch back to reshaping the evidence base — but healthy runs would then lose the routine theme-review moment.
