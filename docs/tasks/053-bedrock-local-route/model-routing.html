How the app chooses its AI models

Every place where the app calls an AI model now asks one committed file which model to use. One setting picks a "route" in that file, and the route decides the model for every step, where the request is sent, and which key it uses. Leave the setting empty and nothing changes: the app calls OpenAI exactly as before. Set it to bedrock-local and every call goes to Amazon Bedrock in London instead.

Why this exists

Before this change, model names were written in 29 places in the code, and nine environment variables could override some of them. Nobody could see in one place which model the app was using, and moving to a different provider meant editing code across the whole backend.

Nesta wants the app's AI calls to run through Amazon Bedrock, Amazon's hosted service for AI models, so that usage is billed and governed through the organisation's AWS account. Bedrock serves the same GPT-5.6 family the app already uses, plus Claude and Cohere. This change makes that move possible with one setting, and keeps today's behaviour as the default until the deployment work is done.

In one sentence: model names now live in backend/src/policy_atlas/model_routes.toml, and POLICY_ATLAS_MODEL_ROUTE picks which set of them the app uses.

Diagram 1: steps, tiers and models

The file has three layers. First, it lists every step that calls a text model and gives it a tier: a role such as "cheap and fast" or "strong writer", not a specific model. Second, each route says which model fills each tier. Third, a route may make a single step an exception, though none of the shipped routes does. The code only ever asks "which model for the screen step?", and the route answers.

The tier is what makes a route short. Moving all fourteen "mini" steps to a new model is one line in the file, not fourteen code edits.

Diagram 2: where a request goes

When the app starts, it reads the route once and keeps it. Three kinds of call then follow the route. Text models (all 27 steps) use the OpenAI client library the app already had; Bedrock offers an address that accepts the same request format, so only the address and the key change. Embeddings and Claude need Amazon's own client library, boto3, because Bedrock serves them in its own request format.

Diagram 3: which key is used

Each route names the setting that holds its key. Both keys can be set at the same time, and in staging and production the plan is to keep both in the app's secret store. Switching route then changes the key that is used without anyone editing a secret, and the OpenAI key is never sent to Amazon.

Diagram 4: embeddings and switching route

An embedding is a list of numbers that represents what a piece of text means, so the app can find passages close to a question. Numbers from two different models cannot be compared. So every stored embedding carries a label, its profile, and the app only ever reads embeddings whose profile matches the current route.

How to

Use Bedrock locallyCreate a Bedrock API key in the AWS console (Bedrock, then API keys; a short-term key lasts up to 12 hours). In backend/.env set: 
POLICY_ATLAS_MODEL_ROUTE=bedrock-local
AWS_BEARER_TOKEN_BEDROCK=<your key>
Restart the backend. Remove the route line to go back to OpenAI.
Try a model without a pull requestWrite a small file with your own [routes.my-test] table (copy one from the route file), then: 
POLICY_ATLAS_MODEL_ROUTE_FILE=my-routes.toml
POLICY_ATLAS_MODEL_ROUTE=my-test
The extra file can add or replace routes. It cannot change the list of steps.
Change a model for goodEdit the model line in model_routes.toml and open a pull request. The change is one line, visible in review, and every step on that tier follows it.
Find which model a step usesFind the step under [steps] to get its tier, then read that tier in the route's .text table. The file has a comment beside each choice that is not obvious.
Retired settings. The old per-step settings such as POLICY_ATLAS_SYNTHESIS_MODEL are ignored. If one is still in your .env, the app logs one warning naming it at start-up; delete it.

A mistake in the route file stops the app at start-up with a message naming the file and the line's key: an unknown route, step or tier, a misspelt backend or key setting, or a section with the wrong shape. The one value it cannot check is a model name written directly as a step exception, because any text could be a valid model id.

How it was tested

  • Nothing changes by default. A test checks that all 29 model settings in the code equal the values they had before this change when no route is chosen.
  • Offline test suite. Over 3,600 backend tests run with network access blocked; the test setup clears the route and key settings so a developer's .env cannot switch a test to a live provider.

Not in this change

DeploymentStaging and production still call OpenAI. A later change adds the Bedrock key to the app secret, sets the route per environment from config, and settles AWS access, quotas and the region policy for the global profile.
QualityLuna in place of gpt-5.4-mini, Terra in place of gpt-5.5, Claude for query writing and Cohere embeddings are not yet measured against the evaluation sets. The overlay file is how those comparisons will run.
