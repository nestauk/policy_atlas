Part 1 · How the code works

1. The files and what each one owns

All paths below are under backend/src/policy_atlas/. Each file has one job, and the boundaries are strict: the search loop never talks to the network, the ranking functions never touch the database, and the persistence step never makes a search call. That is what makes the parts testable on their own.

2. The layers

A search starts when the runner reaches the acquire component of a plan; screening starts at screen_abstract. The harness wraps each component the same way: it opens a run, hands the component a database connection and the scope's context, and records the outcome.

The backends in state are injected. In production they are the live HTTP and OpenAI classes; in tests they are scripted objects that answer every call from fixtures and record what was asked. That is why the whole search pass can be tested with zero network traffic (test_fixture_mode_runs_the_single_pass_with_zero_egress).

3.1 run_search: the entry point

The function reads the scope's directive (depth, filters, guidance), validates the filters for each database, makes the one query-generation call, and then runs the two database legs on two threads. Each leg gets its own _Pass object, which holds that leg's budget and every call it made, so the two threads never write to the same state. When both are done, the calls are merged in backend order and handed to acquire_sources with the two ranked pools and the two caps.

        outcome = future.result()                    # (pool entries, leg summary[, local filters])

3.2 _CallSpec and _Pass: one planned call, and the budget

Every request the pass makes is first written down as a _CallSpec: what verb it is, what text or ids it sends, which filters go on the wire, how many records to take, a closure that performs the fetch, and an optional local filter. A spec is inert; _Pass.execute or _Pass.execute_batch runs it. The budget is counted in logical calls: one spec is one call, however many pages or retries the transport needs underneath. A spec past the budget is skipped and recorded as skipped.

@dataclass(frozen=True)
class _CallSpec:
    verb: CallVerb                       # search, search_semantic, fetch_references, fetch_citations, fetch_by_id
    query: str
    origin: QueryOrigin                  # generated, variant_sr, semantic, snowball_backward, landmark, …
    wire_params: dict[str, str]          # filters sent to the database
    max_records: int
    fetch: Fetch                         # closure: size -> records
    keep: Callable[[dict[str, Any]], bool] | None = None   # local filter, counted as post_filter_excluded


class _Pass:
    def _reserve(self, backend) -> bool:
        """Claim one logical call against the backend's budget, in plan order."""
        budget = self.constants["call_budget"].get(backend.name, 0)
        budget *= self.variant_count.get(backend.name, 1) if backend.name == "openalex" else 1
        if self.calls.get(backend.name, 0) >= budget:
            return False
        self.calls[backend.name] = self.calls.get(backend.name, 0) + 1
        return True

    def execute(self, backend, spec: _CallSpec) -> ExecutedCall | None:
        if not self._reserve(backend):
            return None
        try:
            fetched = spec.fetch(spec.max_records)
        except Exception as exc:
            fetched = exc                            # an error is a recorded call with status "error"
        return self._finish(backend, spec, fetched)

sourcing/search_loop.py · _CallSpec, _Pass._reserve, _Pass.execute

execute_batch is the concurrent form: it reserves the budget for each spec in plan order, runs the fetches on up to 8 threads (SEARCH_CONCURRENCY), and then records the results in plan order, so the events, counts and pool order are the same as a sequential run whatever the thread timing. The pacing lock in the transport (section 6) keeps the request rate within the database's limit however many threads are sending.

One detail that explains a lot of the bookkeeping: _finish copies every returned record (dict(record)) and remembers which call returned it in origin_of, keyed by the Python object id. The pool functions pass record objects around, and at the end entries() looks each one up to say which call found it. That is how every kept document gets its query_origin.

3.3 _openalex_leg: the paper pool in seven steps

  1. Seeds. Build 15 keyword specs (5 queries × 3 forms: as written, with the systematic-review clause, with the trial clause) per filter variant, plus 8 semantic specs (the question, 2 paraphrases, 5 queries). Run them as one concurrent batch.
  2. Fallback. If every keyword call came back empty, search the question verbatim once per variant and say so in the summary.
  3. Interleave. Merge the 23 result lists by taking the top of each in turn (pool.interleave); the first 200 distinct works are the seeds. Count how many seeds cite each work (pool.count_references).
  4. Citation filters. The citation calls carry every wire filter except the author-country one, which is checked locally on the papers that come back.
  5. Backward. The 200 most cited non-seed works, fetched by id in 4 concurrent calls of 50.
  6. Forward. The papers citing the 20 best-connected seeds (each under 300 total citations), fetched page by page until a short page or page 10, then scored and cut to 200 (pool.score_forward).
  7. Pool. Seeds, backward and forward become one candidate list, duplicates are removed, the list is ordered by the three-list mix, and every record the leg ever fetched is listed once for acquire.

The forward loop is sequential on purpose: page 2 is only requested if page 1 was full, and "full" has to count the records the local country filter removed, otherwise a heavily filtered page would look short and stop the chase early.

3.4 _overton_leg: the policy pool in four steps

Three searches go out one after another (Overton's rate limit is slow, 1.2 s between requests, so there is nothing to gain from threads here): the question and the two paraphrases, each asking for best-match order and 134 documents (400 ÷ 3, rounded up). The lists are interleaved and de-duplicated by normalised title (pool.dedupe_policy). Each Overton record already lists the policy documents it cites, so pool.count_policy_cites counts, across the results, how often each document is cited. The 15 most cited that the search did not return are fetched by id (the landmarks), with the plan's country filter applied to them. pool.rank_policy orders results and landmarks together and the leg returns its entries.

A plan whose country filter needs Overton's post-filter form fails closed: if the backend object has no search_with_post_filter method the leg raises rather than search unfiltered.

3.5 entries(): why every fetched record is listed, not just the ranked ones

def entries(self, ranked: list[dict[str, Any]], backend_name: str) -> list[PoolEntry]:
    """The pool handed to acquire: the ranked records, then every other record."""
    self.ranked_count[backend_name] = len(ranked)
    placed = {id(record) for record in ranked}
    out = [(record, *self.origin_of[id(record)]) for record in ranked]
    for call in self.executed:
        if call.backend_name != backend_name:
            continue
        for record in call.records:
            if id(record) not in placed:
                placed.add(id(record))
                out.append((record, *self.origin_of[id(record)]))
    return out

sourcing/search_loop.py · _Pass.entries

Acquire promises that every record a call returned is counted exactly once (kept, already held, unusable, or over the cap). The ranking drops duplicate copies and the records it never placed, so those are appended after the ranked list. The cap passed to acquire is never larger than the ranked count, so the appended tail can only ever be counted as "over the cap". The invariant holds and the cut is still exactly the ranked list.

Three snippets carry most of the method. The scores are rounded to three decimals on purpose: near-equal scores then tie, and the next sort key (weighted coupling, in-set count, seed position) decides, which keeps the order stable and explainable.

def _specificity(inset: int, coupling: int, cited_by_count: int) -> float:
    """Dampen local graph signals when a work is globally cited everywhere."""
    return round((inset + coupling) / log10(cited_by_count + 10), 3)


def query_fusion(lists: list[list[dict[str, Any]]]) -> dict[str, float]:
    scores: dict[str, float] = {}
    for records in lists:
        for rank, record in enumerate(records):
            work_id = record_short_id(record)
            if work_id:
                scores[work_id] = scores.get(work_id, 0.0) + 1.0 / (RRF_K + rank + 1)   # RRF_K = 60
    return scores


def rank_mix(cands, lists, *, novel_from_year, coupling_lists=COUPLING_LISTS):
    strata = mix_strata(cands, lists, novel_from_year=novel_from_year, coupling_lists=coupling_lists)
    out, seen = [], set()
    cursors = [iter(stratum) for stratum in strata]        # relevant, seminal, novel
    while cursors:
        for cursor in list(cursors):
            for candidate in cursor:
                if id(candidate) not in seen:            # skip a paper another list already placed
                    seen.add(id(candidate))
                    out.append(candidate)
                    break
            else:
                cursors.remove(cursor)                     # this list has run dry
    return out + [c for c in rank_papers(cands) if id(c) not in seen]

A small thing to know. The seminal list in mix_strata holds every candidate, so the round-robin places every paper and the last line of rank_mix never adds anything. The tail of the pool, after the relevant and recent lists run dry, is therefore in in-set-citation order, not specificity order. The task 052 notes and the ADR describe the fallback as if it ran; the tutorial's diagram A4 describes what actually happens. Harmless, and worth cleaning up when the file is next touched.

5. acquire.py: from ranked pool to database rows

acquire_sources makes no search call. It receives the executed calls and the two ranked pools, and does four things in order: it writes one search.executed event per call (success or error, with the query, origin, verb, filters and result count); it walks each pool to its cap; it writes the tags and the coverage record; and it embeds the chunks it created. The walk is the part to understand.

for name in names:
    counts = by_backend[name]
    cap = caps.get(name)
    for index, (record, origin, verb) in enumerate(pools.get(name, [])):
        # The cap is a cut on the ranked list by position: a ranked entry the task
        # already holds, or that is unusable, is not refilled from beyond the cut.
        if cap is not None and index >= cap:
            counts["dropped_over_cap"] += 1
            continue
        candidates = map_records(backend_name=name, verb=verb, records=[record], counts=counts,
                                 origin=origin, count_results=False)
        if not candidates:              # no title or no id: counted as skipped_unusable inside map_records
            continue
        candidate = candidates[0]
        if not is_new(candidate):         # record id, DOI or identical text already in this task
            counts["already_acquired"] += 1
            continue
        persist(candidate, pool_rank=index + 1)
        kept += 1

sourcing/acquire.py · acquire_sources, the cap walk (abridged)

Two choices here are deliberate and easy to get wrong. The cap test comes before the identity test, because is_new claims the keys it checks: testing a record we are about to drop anyway would make a later genuine copy look already held. And the cut is by position, not by count of kept records: if the task already holds 10 of the first 100, Focused keeps 90, not 100. The persisted set is always a subset of the first cap ranked entries, which is what makes recall at a smaller cap derivable from a larger run (the eval uses pool_rank for exactly that).

map_records turns a raw provider record into the app's envelope (title, abstract, year, DOI, language, backend, record id, type, publisher) plus a provider_fields block that keeps the fields the ranking and later stages need: citation count, authorships, topics, keywords, open-access block, retraction flag, and the first 60 referenced works. An OpenAlex abstract arrives as an inverted index and is rebuilt into text here. A record without a title or an id is unusable, because there is nothing to screen and nothing to re-identify on a re-run.

6. search_live.py: talking to the two databases

Every request goes through one method, _TransportMixin._request_json, which does the things you would otherwise have to remember in every caller: it waits for the pacing interval, retries on 429 and 5xx up to 4 attempts with doubling backoff, times out at 30 s, caches successful responses for an hour (keyed without the API key), validates the response shape, and strips keys from any error it raises. Because the search now sends 8 OpenAlex requests at once, the pacing changed from "sleep before each request" to a lock: one thread at a time sleeps and stamps the time, the request itself runs outside the lock. A "too many requests" reply pushes every later admission out by a second, and several refusals at once pause once, not several times.

def _pause_admission(self, seconds: float) -> None:
    """Push every later admission at least ``seconds`` away."""
    with self._pace_lock:
        latest = self._last_request_at or 0.0
        # Pauses coalesce: eight threads refused at once pause once, not eight times over.
        self._last_request_at = max(latest, _monotonic() + seconds - self._min_interval_s)

7. Screening, function by function

screen_sources reads the scope's screening directive (which stage, any extra criteria, whether this is a re-screen), folds the criteria into the intent text, and calls _run_stage1. Stage 1 then:

  1. Loads every document of the task that has no non-failed stage-1 row yet (_load_stage1_docs). A re-screen loads all of them into a fresh generation. Each document is tagged title_abstract or title_only.
  2. Sets aside retracted documents before any model call, writing an excluded_retracted row for each (_exclude_retracted_docs). Retraction is a policy exclusion, never a relevance verdict.
  3. Runs batch 1: one call per document on 12 threads, one retry for a failed call (_run_stage1_calls).
  4. Runs batch 2 for the documents whose first reply was not_relevant.
  5. Decides each document with the pure table decide_stage1, writes its row and its event, and totals the counts.
run_batch([(doc_index, 0) for doc_index in range(len(docs))])
second_tasks = [
    (doc_index, 1)

    if (first := results.get((doc_index, 0))) is not None and first.decision == "not_relevant"

def _p_relevant(rep: ScreenRepWire) -> float:
    if rep.decision == "relevant":
        return float(rep.confidence)
    if rep.decision == "not_relevant":
        return 1.0 - float(rep.confidence)
    return 0.5                                                 # unsure


def decide_stage1(first: ScreenRepWire | None, second: ScreenRepWire | None) -> Stage1Decision:
    if first is None:
        return Stage1Decision("failed", None, ())
    if first.decision in ("relevant", "unsure"):
        if second is not None:
            raise ValueError("second stage-1 call supplied after a kept first reply")
        return Stage1Decision("relevant", _p_relevant(first), ())

    if second is None:
        return Stage1Decision("not_relevant", 1.0 - _p_relevant(first), ("second_call_failed",))
    mean_p = (_p_relevant(first) + _p_relevant(second)) / 2
    if second.decision in ("relevant", "unsure"):
        return Stage1Decision("relevant", mean_p, ("second_call_kept",))
    return Stage1Decision("not_relevant", 1.0 - mean_p, ())

assess/screen.py · _p_relevant, decide_stage1 (complete)

The whole decision is these twelve lines, and they take no connection and make no call, which is why the screening eval under scripts/evals/screening/ imports this function and replays recorded replies through it rather than re-implementing the rule. The stored confidence is the mean probability of relevance over the calls made, so a confident "no" followed by an "unsure" is kept with a confidence near 0.5, visibly shaky.

The model call itself is in OpenAIScreeningBackend.screen_envelope: it builds the messages from screen_v4, asks for structured output in the ScreenRepWire shape (decision, confidence, one-line reason), wraps the call in a traced span named screen:abstract, and rejects a confidence outside [0, 1]. The prompt's rules that changed in screen_v4 are the ones the task 050 eval found costly: a different population excludes only when the intent names one; a match on the main subject with one other element different is relevant or unsure, never not relevant; a criterion the abstract does not report never excludes.

8. What a run leaves behind, and where to look first

When a search or screen looks wrong, the record is usually enough to explain it without a trace. In order of how often they answer the question:

  • event_log, type search.executed: one per call, with the query text, its origin, the verb, the filters sent, the status, the error text, the result count, how many pages it took and how many records a local filter removed. The order is the plan order. If a database call failed, this is where it says so.
  • event_log, type source.acquired: one per kept document, with query_origin and pool_rank. Join on task_source_snapshot_id to find out why a document is in the task and where it ranked.
  • event_log, type source.screened: one per screened document, with every model reply (decision, confidence, one-line reason) and the flags. This is where "why was this dropped" is answered.
  • component.completed payload for the acquire run: the acquire counts plus counts["search"] (depth, calls per backend, zero-result queries, dropped queries, fallback, seeds, backward targets, forward candidates, duplicate papers, landmarks, pool sizes, wall clock, locally applied semantic filters).
  • search_coverage_record: one row per acquire run, with the filters as sent, the local filters, the post-filter exclusions per call, the stop condition (completed or error) and the adequacy verdict (inadequate if any backend errored or nothing usable came back).
  • Langfuse: the trace for the run has the query-generation span (input, output, tokens, prompt version) and one screen:abstract span per screening call. Use it for model input and output; use the event log for everything else.

To watch a whole run on a question of your choice without writing to the database, the eval engine does exactly that: scripts/evals/search/checks/engine.py seeds a throwaway task in a transaction, calls the real run_search and screen_sources, scores the result and rolls back. checks/production_recall.py --reviews TEXT --depths rapid runs it for one ground-truth review; checks/inspect_run.py unpicks a run afterwards.

10. What was deleted, and how to get it back

The round loop and its four strategies are gone from the product: in search_loop.py the constants ROUND_CAP, POS_EXEMPLARS, NEG_EXEMPLARS, SNOWBALL_SEEDS, SNOWBALL_RESULTS, SHORT_CIRCUIT_RATE, DIVERSITY_FRACTION and the four call caps; the classes _ScreenedRecord and StopDecision; the functions that read screened documents as exemplars, evaluated the stop rule and wrote it to the coverage record; and in runner.py the gate that re-opened acquire and screen for another round. In screen.py the three-sample majority with its quorum and tie-break went with them. The tests that pinned the loop were deleted with it.

Two things were kept on purpose. The reformulate and suggest prompt builders, their output schemas and backend methods stay in search_prompts.py and search_generation.py, tested but unreachable from the runner, because the prompts are the expensive part to recreate if the parked "second search for Broadest" is ever built (docs/deferred.md). confident_relevant_count and its two thresholds were kept at first for the same contingency, then deleted at the PR review (2026-10-14); they are at the same tag.

The last commit on which the loop ran end to end is tagged search-round-loop-last. The restore recipe in ADR 0038 decision 8 is git checkout search-round-loop-last -- <path> for search_loop.py, runner.py and the two deleted test files, then re-wiring a strategy's output to the pool hand-off of section 3.5. Old coverage records keep their old stop vocabulary and remain readable.

11. The tests, and how to read them

Run them from backend/ against the test database (the conftest refuses the development one):

DATABASE_URL="postgresql+psycopg://policy_atlas:policy_atlas@localhost:5432/policy_atlas_test" \
  uv run pytest tests/evidence_search/sourcing/test_pool.py \
                tests/evidence_search/sourcing/test_search_single_pass.py \
                tests/evidence_search/sourcing/test_acquire_pools.py \
                tests/evidence_search/assess/test_decide_stage1.py -q

four files, about 45 tests, no network, under a minute

  • test_pool.py (12 tests): pure functions with hand-made candidates, plus one replay of a recorded experiment pool (tests/data/pool_fixture.json) that pins the exact ranking a real question produced. Start here: the _cand helper shows which fields matter.
  • test_search_single_pass.py (25 tests): the whole pass with scripted backends that answer every verb from fixtures and record each call. The tests assert the exact call plan: how many calls, in what order, with which filters, what happens when a budget runs out, when a call errors, when every query comes back empty. The two concurrency tests check that thread timing never changes the recorded order.
  • test_acquire_pools.py (5 tests): the hand-off. Two pools, two caps, the count invariant, and that nothing beyond the cap is persisted or embedded.
  • test_policy_replay.py (3 cases): recorded Overton responses for three questions replayed through the pure policy rules, checking the order, the title de-duplication, the 15 landmarks, the scores, a UK-only filter and the cut.
  • test_decide_stage1.py: the full decision table as parametrised cases, and the guard against a second reply after a kept first one.
  • test_search_live.py (45 tests): the transport with an injected fetch function and a recorded sleep: pacing, retries, the cache, redaction, the response-shape checks.

The pattern to copy when you add behaviour: put the rule in pool.py or decide_stage1 as a pure function with a unit test, and let the integration test in test_search_single_pass.py assert only that the function is called in the right place with the right inputs.

12. A reading order

  1. The tutorial, diagrams A1 to A4 and B, for the method and the numbers.
  2. pool.py top to bottom. It is the method in code and has no dependencies; test_pool.py beside it shows each function on a small example.
  3. search_loop.py: DEPTH_CONSTANTS, then _CallSpec and _Pass, then _openalex_leg and _overton_leg, then run_search. Skip the filter validation functions on a first pass; they are long and mechanical.
  4. acquire.py: only acquire_sources, from the identity preload to the cap walk. The mappers above it are what the envelope fields mean.
  5. screen.py: decide_stage1, _run_stage1_calls, _run_stage1, then screen_prompt.py for the prompt text.
  6. search_live.py: _request_json and one verb of each class. The rest is sanitisers and guards you will only need when a provider misbehaves.
  7. ADR 0038 for the decisions and their evidence, then the task notes (notes.md in this folder and in 052-rank-mix-paper-dedupe/) for what was tried and rejected.
